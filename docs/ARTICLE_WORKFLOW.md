# 文章製作流程：從選題到上線追蹤

目標：每篇文章都要**對讀者有用**（解決他搜尋時想解決的事）、**好讀**（掃得過去、找得到自己要的段落）、**好檢索**（搜尋引擎和 AI 摘要看得懂這頁在回答什麼）。

這份是總流程。用教練影片當素材時，素材那一段的細節在 [`COACH_ARTICLE_WORKFLOW.md`](COACH_ARTICLE_WORKFLOW.md)。

| 階段 | 產出 | 在哪裡做 |
|---|---|---|
| 1. 選題 | `docs/briefs/<slug>.md` 選題卡 | 搜尋建議要在站主電腦抓，其餘雲端 |
| 2. 素材 | 規則書段落、廠商規格，或 COACH-SYSTEM.md | 規則／球拍在雲端；教練影片在站主電腦 |
| 3. 大綱 | 選題卡裡的大綱段 | 雲端 |
| 4. 寫作 | `src/content/articles/<slug>.mdx` | 雲端 |
| 5. 查證 | 查證紀錄 | 獨立的 subagent；教練影片類在站主電腦 |
| 6. 上線 | draft PR，站主看預覽後合併 | 雲端 |
| 7. 追蹤 | 選題卡裡的追蹤段 | 上線後第 4 週、第 8 週 |

## 1. 選題

一個題目要同時過三關才寫：

1. **有人搜**：讀者用中文搜得到這個說法。
   - 在站主電腦跑 `python -X utf8 scripts/topics/suggest.py 匹克球 匹克球拍 …`，看 Google 自動完成。
   - 用 Google Trends 比幾個說法的相對熱度，例如「匹克球 規則」對「匹克球 計分」。
   - 網站有數據以後，看 Search Console 有曝光、但排名在 8 到 30 名，或沒有對應頁面的查詢。
2. **我們有可信的素材**：
   - 規則題要有 USA Pickleball 規則書的條文。
   - 球拍題要有廠商規格。
   - 技術題要有 COACH-SYSTEM.md 裡至少 15 條相關的 verified 條目。
3. **站內還沒有人回答**：不跟現有文章搶同一個查詢。已經有的題目就補進舊文，不另開新篇。

台灣的現況（`docs/PLAN.md`）：規則、球拍、入門、哪裡打的需求最大，中文技術詞（dink、第三拍）幾乎沒人搜。所以**技術文要掛在有人搜的說法上**，例如「匹克球 新手」「匹克球 技巧」「匹克球 發球」，不要用「dink 技巧大全」當主題。

選好後複製 `docs/briefs/_TEMPLATE.md` 寫一張選題卡。寫不出「讀者搜這個想解決什麼」的題目，就先不寫。

## 2. 素材

- **規則**：對照 USA Pickleball 現行規則書原文，記下條號。
- **球拍**：對照廠商規格頁，價格標「（來源、YYYY-MM 查證）」。
- **教練影片**：照 `COACH_ARTICLE_WORKFLOW.md` 第 1 到 8 步，產出 COACH-SYSTEM.md，文章只用裡面 verified 的條目。

型號、店名、場館、組織名稱查不到就不寫。

## 3. 大綱（寫在選題卡裡，寫正文前先定）

**標題**
- 主關鍵字放最前面，例如「匹克球新手常犯的錯誤」。
- 冒號後面講讀者得到什麼，例如「先少丟分，再修每一拍」。
- 全長 32 字以內，超過的話搜尋結果會被截斷。

**description**
- 50 到 120 字，包含主關鍵字。
- 說清楚這篇回答什麼、素材來自哪裡。

**開頭三段**
- 先回答讀者最想知道的事，或給一句總結，再講這篇怎麼排。
- 不要用故事或背景鋪陳開場。

**H2**
- 每個 H2 是讀者會問的一個問題，或要做的一件事。用讀者會搜的說法，例如「誰喊界外」，不要寫成「判決權歸屬」。
- 4 到 8 個。冒號前 16 字以內，右側段落軌才放得下。
- 真的有先後順序才用「第一步：…」，段落軌會自動顯示步驟數字。

**每個 H2 的第一句就是結論**
- 讀者只看這一句也能得到答案。
- 搜尋引擎和 AI 摘要也最常摘這一句。

**takeaways**
- 3 到 5 條，每條一句完整的話，會顯示在文章頂端的重點框。

**常見問題**
- 搜尋建議裡零碎、但一兩句就能答的問題，放在文末，用 `<details><summary>問題</summary>回答</details>`（寫法見 `pickleball-rules.mdx`）。

**連結**
- 往外連：列出要連到哪 2 篇以上的站內文章。
- 往內連：列出要從哪篇舊文加連結進來。

## 4. 寫作

**好讀**
- 一段只講一件事，大約 4 行內（200 字左右）。並列的東西用清單，有比較的用表格。
- 大約每 2,500 字至少放一個圖解、表格或影片卡，讓讀者捲動時有地方停。
- 術語第一次出現時附說明。用字照 `docs/TERMINOLOGY.md`。
- 教練影片類：內文不放時間點，關鍵段落結尾放 `VideoRef` 卡，一篇 5 到 6 張就夠。

**可信**
- 規則附條號。價格和精確數字附「（來源、YYYY-MM 查證）」。
- 英制單位附公制換算：3 ft ≈ 90 cm、4 ft ≈ 1.2 m、7 ft ≈ 2.13 m。
- 教練的建議寫成「教練建議」，不要寫成定論。
- 編者自己的整理（例如排序）要明講是我們整理的。

**格式**
- 粗體的結尾 `**` 前面不能是全形標點。
- 改內文數字時，frontmatter 的 description 和 takeaways 也要一起改。

可用元件：

| 元件 | 用途 |
|---|---|
| `StepGuide` | 開頭的步驟帶 |
| `VideoRef` | 影片縮圖卡 |
| `fig/*` | 球場、球拍、發球等圖解，圖說標「示意圖」 |
| `ArticleCover` | 依 slug 關鍵字挑封面，新題目可以加一種 |

## 5. 查證

派一個**沒寫過這篇**的 subagent，目標是找錯，逐句對照一手來源：

- 規則對規則書原文。
- 球拍數字對廠商規格。
- 教練影片類照 `COACH_ARTICLE_WORKFLOW.md` 第 10 步，對字幕。

description、takeaways 也要查。error 全部修完才上線；minor 逐條判斷。

## 6. 上線

```
npm run check:articles -- <slug>   # ✗ 一定要修，△ 自己判斷
npm run check                      # 0 errors
npm run build
grep -rlF "**" dist --include=index.html   # 應該沒有結果
```

`check:articles` 會檢查這些：

- 標題和 description 的長度、takeaways 條數、H2 數量。
- 段落是不是太長、圖和影片卡夠不夠。
- 站內連結：往外連幾篇、有沒有連到不存在的文章、有沒有舊文連進來。
- 粗體有沒有失效、內文有沒有殘留時間點、英制單位有沒有換算。

最後照選題卡在舊文加上連進來的連結，開 draft PR，站主看過預覽說可以才合併。

## 7. 追蹤

在選題卡的「追蹤」段記兩次。

**第 4 週**看 Search Console 這頁的查詢：
- 有曝光、但文章沒正面回答的問題，補一段或一個常見問題。
- 標題跟實際帶來曝光的說法差很多時，考慮調整標題。

**第 8 週**看曝光、點擊和平均排名，跟同類文章比。

改內容時才更新 `updatedDate`，沒有實際改內容就不要更新。
